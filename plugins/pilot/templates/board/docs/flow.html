Story Board — how the build flows

What runs, in what order, and what happens when each step fails.

factory-board · generated from the code, not from the spec

The board is a projection of two things it does not own: markdown files in the repo, and live git state. Nothing here is hand-maintained, which is why it cannot drift the way a hand-updated board does. Every stage below either takes data and returns data, or shells out — never both.

Stages, in execution order

01 Read git and GitHub facts impure lib/github.mjs → readGitFacts()

The only module in lib/ that shells out, deliberately — one place to get graceful degradation right instead of several. Runs gh pr list --state all --limit 500, resolves a default branch, lists refs/heads/ and refs/remotes/origin/, then reads pilot cycle files. Every call goes through safeRun, which turns a rejection into a non-zero exit so no call site can throw.

02 Parse epics from the BRD pure lib/epics.mjs → parseEpicsWithDuplicates()

Slugs come from an explicit <!-- epic: slug --> marker, never from the heading text. Heading text gets edited for readability; deriving slugs from it would silently reparent every story under that heading. A repeated slug is a mistake, not a request for two lanes — the first wins and the repeat warns.

03 Parse each Technical Design Document pure lib/tdd.mjs → parseTdd()

YAML frontmatter plus a markdown body. A leading UTF-8 BOM is stripped first — Windows editors write one by default, and it used to push the file into quarantine as "missing YAML frontmatter", an error naming the wrong cause. A BOM appearing later is content and is left alone. Failures raise TddParseError, which the caller catches; anything else is a real bug and propagates.

04 Validate the story set pure lib/validate.mjs → validateStories()

Returns three buckets, and which bucket a problem lands in is the whole design: errors stop the build, invalid quarantines one story and the build carries on, warnings still render the story. One developer omitting points_initial must not blank the board for the whole team.

Only two things are fatal, and both are genuinely ambiguous rather than merely wrong: a duplicate id (the build cannot guess which file owns it) and a dependency cycle (it cannot guess which edge to drop). Cycle detection deliberately still spans quarantined stories — a cycle is a property of the graph as written, and hiding it because one member also had a bad points value would let it survive to the next build.
05 Derive each story's status pure lib/status.mjs → deriveStatus()

Takes the story and the git facts, returns a status and the reason for it. Never asks the filesystem or the network anything. This is the module the whole board's credibility rests on, and it is the one module the pilot integration was forbidden to touch.

06 Attach pilot's cycle as a sub-status pure lib/pilot.mjs → projectPilot() · build-board.mjs → resolvePilot()

Enriches an in-flight card with the phase pilot's autopilot is actually in. Never participates in status derivation — see below.

07 Assemble and write the artifact impure scripts/build-board.mjs → buildBoard() + main()

Reads prompt bodies (confined to the repo root first — a prompt: value is author-controlled text and ../../../../.ssh/id_rsa was once read and embedded verbatim), derives the project key from the most frequent id prefix, and writes board.json. The write is the last statement on purpose: a failed build must leave no artifact rather than a partial one, and must not overwrite a good previous build with wreckage.

Status precedence

Evaluated top to bottom; the first match wins. Merging is terminal and irreversible, so it outranks recency — an older merged PR beats a newer open one.

ConditionStatusstatusSource

A PR matches a story if the story id appears in the head branch (bounded by / or -, which is what stops JYO-4 matching JYO-40) or in the PR title. A closed-but-unmerged PR falls through deliberately: the work was abandoned, so the branch is the better signal.

Pilot cycle resolution

Optional. If a story's branch carries an autopilot cycle, the board publishes it as pilot plus a pilotSource saying which tier answered. Candidates come from both branch refs and PR head branches — refs alone missed every story whose branch this clone never fetched.

TierReadpilotSource
1git show origin/<branch>:.pilot/cycles/<slug>.jsonremote:origin/<branch>
2<repo>/.pilot/cycles/<slug>.jsonlocal
3nothing foundnull
Pilot never overrides status. A cycle is one agent's self-report and outlives the session that wrote it; status stays derived from facts other people can independently see. A cycle claiming done cannot promote a story that only has a branch — and a story that has actually merged drops its cycle entirely, because shipped work outranks a self-report. There is deliberately no staleness timeout: the cycle's own updated timestamp travels in the artifact and the reader judges.

What triggers what

TriggerRunsEffect
npm run start-story -- JYO-4 scripts/start-story.mjs Reads the TDD, derives <id>-<slug>, checks the branch out. The frontmatter id wins over the typed one, and says so when they differ.
npm run build [repo] [--verbose] scripts/build-board.mjs The whole pipeline above. Writes board.json, prints one summary line to stdout.
Pull request opened ci/branch-name.yml → ci/run-check.mjs Rejects a branch that resolves to no story. chore/, hotfix/ and docs/ are exempt — case-sensitively, so a typo cannot bypass it.
npm test node --test 209 tests, no framework, no bundler.

There is deliberately no local git hook enforcing branch names. Hooks are not cloned and --no-verify skips them, so they enforce nothing you can rely on. CI is the real net; start-story is the ergonomic path that means you rarely meet it.

All three entry points agree that a story id comes from frontmatter, never from the filename. start-story prefers the frontmatter id over the one you typed (and says so), build-board quarantines an id-less story, and run-check skips one rather than falling back to its filename — otherwise a branch could pass CI by naming a story the board itself refuses to show.

One caveat that is true of this repo only. ci/run-check.mjs resolves tdd/ as ../../tdd, which is correct once the board is vendored into an app repo at board/ — and wrong here, where the directory is factory-board/ at the workspace root. The check is right about where it expects to live; this repo is the exception. Left as-is deliberately.

Seeing it run

BOARD_DEBUG=1 or --verbose narrates the pipeline to stderr — stdout carries the summary line a caller may parse. Silent otherwise. Tracing lives only at the two boundaries, orchestration and the shell-out module; the pure modules stay untraced, and what they did is visible in the traces on either side of them.

Degradation

The governing rule is that every failure mode leaves a working board. A dashboard that refuses to render because one file has a typo is worse than useless to a team that depends on it.

FailureBehaviour
Malformed YAML in a TDDThat story lands in broken[]; build succeeds
Missing required fieldThat story is quarantined; the rest of the board builds
Unknown epicWarning; story renders under Unassigned
gh missing or unauthenticatedDegraded; status falls back to local branch state
Fewer than 500 PRs returnedFine. At exactly 500, warns — a truncated page is indistinguishable from a full one
Missing or escaping prompt pathWarning; the story is untouched
Malformed pilot cyclepilot: null + warning naming the file
Duplicate idBuild fails, both paths printed, no artifact written
Dependency cycleBuild fails, the cycle printed
